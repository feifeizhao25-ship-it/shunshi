# 支付宝退款入口审查（2026-09-13）

## 发现与本轮范围

原公开退款入口只验证订单归属，就把客户端提供的金额交给商户退款接口。底层每次生成新的退款流水号，且没有同步本地付款状态、退款余额或会员权益。不能让这一入口继续把“请求已提交”作为退款完成。

本轮改为**持久化退款申请**，并停止该公开入口直接执行商户退款。这是对不完整退款链路的安全修复，**不是退款执行闭环完成**。没有真实退款、真实扣款或生产切换。

## 当前行为

- POST `/api/v1/payments/alipay/refund` 仅接受当前用户已确认付款、有支付流水、人民币支付宝订单的申请。
- 金额必须能精确转为分，且为正数、不超过订单实付金额。拒绝指数、非数值、多余小数位、负数和超额金额；不使用浮点金额结算。
- 每笔订单保存一份申请。同金额重试或并发提交复用同一 `refund_no`；改金额返回 409，保留原记录。首次填写的原因保留，不借重试修改原申请。
- HTTP 202，中文提示“退款申请已记录，退款尚未执行”，状态为待处理，`refund_completed=false`。`success=true` 只表示申请接口接收成功，不表示已退款。
- GET 同一路径携带 `order_no` 可查询持久化申请；仍校验订单归属。申请不会修改会员期限、付款状态或恢复任务。

## 验证

新增 14 项退款回归，与既有支付检查合计 21 项通过，覆盖金额边界、订单状态/渠道/币种、身份隔离、重复申请、独立连接并发和持久化查询。测试将商户退款调用替换为禁止执行的断言；对照恢复旧路由时，该断言实际捕获了旧入口的商户调用。全部为本地测试，没有商户资金操作。

仓库完整性门禁通过。完整后端回归 **3524 passed、7 skipped、72 warnings，137.03 秒**；日志 `/tmp/shunshi-refund-full-20260913.log`。

## 上线前仍需完成

1. 退款处理后台或受控运维入口、处理权限和可追踪的业务审核流程；目前申请只记录待处理，尚无处理人员通知。
2. 全额/部分退款、已消费期限、续费和跨档订单的权益重算规则，及相应产品说明。
3. 以持久化退款编号执行商户请求、查询不确定结果、校验退款实额、累计余额和幂等结算，不能恢复旧的“每次随机编号直接退款”路径。
4. 退款确认后的本地账本、会员权益、缓存、后台恢复任务协调，验证旧付款通知不会恢复已退权益。
5. 退款记录与账户导出、注销、留存规则的完整衔接，以及真实商户和阿里云生产验收。

在以上闭环完成前，不能向用户承诺自动退款到账或把本项目标为支付上线验收完成。
