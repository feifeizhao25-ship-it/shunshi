# 注销后跨库清理恢复（2026-10-09）

## 已实现

核心账号删除与 AccountErasureJob 持久化任务在同一核心数据库事务提交。任何后续记录库或产品库清理失败，都不会丢失已经提交的清理意图。核心事务回滚时，账号与任务也一起回滚。账号删除先取得与购买恢复、家庭席位相同的账号锁，避免并发购买在删除过程中写回权益。

接口先尝试同步清理，失败返回 deleted=true、erasure_status=pending 和未完成范围，表示账号已注销、其他数据仍待清理。任务记录仅含账号标识、状态、次数、时间和固定错误分类，不存储原始异常、个人资料或凭证。生产生命周期启动清理循环，每轮最多处理 25 个到期任务，每 60 秒检查一次；异常稍后重试，部分表清理不完整则按次数退避（最长 1 小时）。完成任务不再重复执行。

记录库先加写锁，再锁定核心清理任务，遵守与付款恢复相同的锁顺序。各数据库仍独立提交；进程中断后通过重复执行幂等删除恢复，不能描述为跨库原子事务。付款恢复任务属于运行任务，不属于需要保留的付款凭证，注销清理会将它删除。

任务记录同时作为持久注销标识。核心认证依赖与产品路由门禁会检查该标识，在清理尚未完成、应用重启和其他设备使用旧令牌时均拒绝继续操作；完成清理后仍保持拒绝。正式应用由 create_app 提供核心数据库 session_factory，测试中的独立路由装配不新增认证绕过。

## 测试证据

最终专项组合 209 项通过，包括：

- 记录库、产品库分别注入异常后，任务保留、账号移除、旧设备令牌拒绝、到期前不重试、重启后恢复；
- 核心提交前失败时账号仍存在、任务不存在；提交已成功但确认丢失时，任务仍可恢复；
- 部分表未清理不能标记完成；
- PostgreSQL 中两个工作线程竞争同一任务，产品清理只执行一次、最终任务完成；
- 生产模式工作循环实际启动并在退出时停止；
- 原有账号、旧版路径、家庭席位、商店购买恢复、付款恢复及产品门禁回归。

## 部署与边界

新增表遵循现有启动 create_all 建表机制。生产上线前仍需在备份/演练环境确认数据库 DDL 权限及任务恢复效果。工作循环仅在生产模式自动启动，开发测试可调用 recover_pending_erasures 验证。

- 未覆盖升级前已经删除核心账号、又没有持久清理意图的历史残留；这类数据需要另行盘点，不能自动猜测应删除谁。
- 任务完成后的最小注销标识保留策略、运维告警/处理界面仍待完善。
- 本轮验证顺序请求与清理工作线程竞争，未证明所有产品写入与注销同时发生时都已完全串行化；注销前已通过门禁的在途请求仍需进一步审计。
- 没有阿里云真实部署、真实支付或移动端实际 UI 验收，不等于四产品全面上线验收完成。

## 老账号兼容补充

全库第一次执行发现合法邮箱账号没有核心 User 行，不能简单将 UPDATE 核心账号影响零行解释为“账号不存在”。修复后，已验证登录身份的请求在持有记录库写锁时核对旧账号存在且未被注销，也能生成同样的核心库清理任务。不存在的账号仍返回 401，不创建任务。没有为方便注销而伪造核心账号。

这同时说明邮箱/手机号等历史身份入口的核心账号投影尚未全面统一，本轮仅解决其注销兼容问题，不宣称其所有核心会员和导出操作均已贯通。

专项已覆盖邮箱登录与用户数据身份整套回归。生产回滚到不识别注销标识的旧代码前，需要核对待清理任务及账号状态，不能假定旧版本具备同样的拒绝访问能力。

## 旧认证路径补齐

记录库暂时不可用时，旧用户行和旧令牌可能尚未清除。进一步给旧认证模块的个人资料、密码登录、刷新令牌和严格身份依赖加上持久注销标识检查。测试在记录库清理被故障注入阻断时，确认第二设备的访问令牌、刷新令牌和旧式数据库令牌均不能通过相应入口读取个人资料或重新登录。相关回归覆盖现有认证与安全边界测试。
