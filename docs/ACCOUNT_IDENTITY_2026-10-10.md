# 口令账号与核心资料同步（2026-10-10）

实际优先挂载的邮箱/手机号口令注册入口原来只写记录库 users。登录虽然签发核心 JWT，核心 User 却不存在，因而核心资料导出及要求核心账号存在的会员流程会拒绝该用户。

注册现在先保存原有凭据，再以同一用户 ID 补齐核心 User，成功后才签发 token。历史账号在口令验证成功后也执行同一幂等同步。已有核心资料保持原样；同步不复制旧密码散列、不按邮箱/手机号合并账号、不将未验证手机号写入核心短信登录身份，也不根据旧 is_premium 标记授予会员。

同步按记录库 BEGIN IMMEDIATE → 核心数据库的顺序加锁，与注销保持一致；在锁内重新确认记录账号存在且未删除，并检查永久注销标记。锁保持到核心提交完成，避免检查与创建之间被注销穿插。

两库不是分布式事务。若核心同步失败，返回中文 503 且不返回 token，已保存的注册凭据允许通过原密码登录重试。核心已提交而响应丢失的情况也可幂等重试。手机号验证、跨登录方式安全绑定仍需独立完善，不能把这里的资料同步当成手机号认证。

## 验证与范围

专项扩大到账号全链路后为 82 项通过、2 项既有跳过：包括 SQLite/PostgreSQL 下 16 项新用例，以及口令登录、导出身份隔离、旧账号全链路和注销恢复回归。新场景覆盖新账号真实导出、历史账号恢复、错误密码不得建号、既有资料保留、不误授会员、核心提交失败后重试、pending/done 注销标记、并发同步、手机口令入口、同步与注销并发。历史“仅记录库账号注销”测试改为明确构造升级前状态，保留兼容性覆盖。

本批没有验证真实商店付款、短信、云端部署或 UI。第三方登录、仅刷新 token 的历史账号不会通过本次口令登录路径同步；旧登录响应的会员标记仍需统一到权威权益来源。此前已进入处理流程的请求在注销后继续写入的通用问题仍未全部解决。

首轮全量为 3376 通过、408 失败、15 跳过：比基线新增 21 项旧账号夹具失败。定位后将同步服务的记录库连接读取与现有注入方式一致，并为只挂载 auth 路由的轻量测试提供真实核心数据库 session_factory，没有 mock 掉同步、放宽身份校验或降低断言。首轮原始记录也保留供追溯。

最终全量为 **3395 通过、387 失败、17 跳过、58 条警告**，耗时 181.06 秒。与前一批 erasure-scheduling 的失败测试标识集合完全一致；没有新增失败，也没有将增加的 16 项新场景冒充修复了既有失败。仓库完整性、后端部署配置检查和 git diff --check 均通过。尚不能宣布四产品具备全部上线条件。
