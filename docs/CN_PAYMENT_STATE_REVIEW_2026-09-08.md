# 国内支付入口 P0 增量审查

本轮修改顺时旧订阅路由，不代表四项目支付系统全部完成。

- 取消订单要求正式登录令牌且订单归属一致，自报 user_id 无效；取消写入数据库，不再仅修改内存。
- 支付与取消采用数据库 pending 条件更新，旧缓存不能覆盖已经完成的状态。交易号被另一笔订单使用时拒绝入账。
- 支付宝兼容回调必须有匹配的支付平台、非空交易号、成功交易状态、精确对应订单分金额及有效签名。去掉开发环境缺少签名也成功的分支。
- 非法回调不把待支付订单变成 failed；已支付订单的重放仍须验签，交易号必须匹配。
- 旧 Google 仅检查 token 长度、旧 Apple 只看验签 status 的路径不能证明当前 SKU/用户/环境下的支付，兼容入口现在拒绝这些不完整验证。未完成商店交易绑定前保持关闭。

## 验证和边界

首轮相关支付、订阅测试 139 项通过，均为测试密钥签名和本地订单，不是真付款。另补独立 SQLite 连接并发验证支付/取消竞争与交易号跨订单竞争，结果在完成后追加。

现有兼容回调的签名格式不是已通过商户联调的支付宝正式异步通知证明。正式商户通知、应用/卖家/币种核验、支付与权益同事务、退款、续费期限以及主权益表一致性还需继续审查；部分旧账户接口仍有 testing 环境绕过和用户参数，不能称为全 API 鉴权完成。

本轮条件更新针对仓库现用的 SQLite 订单存储；阿里云 PostgreSQL 上线前需要统一数据库与迁移，再跑实际数据库并发测试。不能将 SQLite 的并发结果外推为所有数据库的保证。

旧订单查询缓存、订单已付但权益激活失败的补偿、运行中进程崩溃恢复仍未闭环。未运行生产发布或真实支付，已售权益未修改。

2026-09-08 验证续记：独立 SQLite 连接的两项并发测试通过。全后端首轮 3458 通过、7 跳过、2 失败，失败来自旧旅程仍使用开发环境免验签以及依赖上一测试的会员状态。两项测试已改为测试 RSA 私钥真实签名和独立免费用户，不再放宽生产验证。最终支付、订阅、旅程和并发相关 157 项通过，存在 5 类依赖弃用提示；尚未把局部复跑称为最终全量通过。

最终全量复跑：2026-09-08，提交 73832c75 的后端完整测试 3462 通过、7 跳过、72 条警告，耗时约 140 秒。包括共享额度、支付和独立数据库连接竞争测试。跳过与弃用警告仍需按范围处理；真实支付、生产发布及上述剩余缺口不在这个结论内。

## 2026-09-09 主支付宝通知与部署配置修复

正式通知入口 `/api/v1/payments/alipay/notify` 现在通过实际 `python-alipay-sdk` 验证 RSA2 签名，并核对配置的应用 ID、收款商户 ID、交易标识、状态及精确金额。拒绝重复表单参数、金额舍入、指数、非有限值和零负金额；配置缺失返回 503。成功处理返回纯文本 `success`，不再返回 JSON，避免支付宝因无法识别应答而反复重试。

协议依据：[支付宝服务端异步通知官方说明](https://developer.alibaba.com/docs/doc.htm?articleId=105301&docType=1&treeId=193)，2026-09-09 查阅。依赖为第三方 [python-alipay-sdk 3.4.0](https://pypi.org/project/python-alipay-sdk/)，已加入镜像安装清单。正式部署工作流补齐商户 ID、支付宝验签公钥、通知与返回地址；启用支付宝时要求六项配置齐全且地址使用 HTTPS，全部未配时支付服务仍关闭。

本地支付与订阅回归 231 项通过，其中 25 项新增测试使用独立生成的 RSA 测试密钥与实际 SDK 验签，覆盖签名正确但商户/应用/金额错误的情形。真实 SDK 验签不等于支付宝商户联调或真实付款。部署脚本的缺失、部分配置、完整 HTTPS 配置、HTTP 地址四类检查通过；未执行集群写入。

聊天 RAG 的仓库检查已适配旧入口委托统一入口的实现。三个实际 HTTP 入口均验证网关收到已核验、未过期的参考资料，且返回来源；聊天及旧入口鉴权回归 27 项通过。仓库完整性检查通过。

本批最终全后端回归：3489 通过、7 跳过、72 条警告，耗时 125.98 秒。跳过项、依赖弃用提示和未覆盖的生产行为不计为通过。

仍未完成：主支付激活的支付/取消竞争、跨订单流水竞争、SQLite 订单与 SQLAlchemy 权益分库提交及崩溃恢复、续费期限、退款闭环、正式商户联调、阿里云生产验收。前述旧兼容路由的并发测试不能代替主激活链路的修复与验证。四项目尚不能统一标记为上线完成。
